# tests

pytest suites against fakes. `python -m pytest` from the repository root runs every suite with the system Python. Nothing here imports Honcho, opens the database, or calls a provider. `conftest.py` points every log, status and data path at the test's temporary folder, so no test writes to `/logs`, `/data` or `/config` on the machine running it.

Install the test tools with `pip install -r requirements-dev.txt`. The rerank component's own tests are in `src/rerank/tests/` and need Honcho's Python environment; see `src/rerank/README.md`.

`test_receiver.py` reads `TELEMETRY_SAMPLE` (a jsonl of captured CloudEvents) at run time and posts the first 200 lines. That test skips when the variable is unset. The other receiver tests cover the token, the body cap and `MAX_BODY_MB`, untrusted framing (chunked, signed or repeated `Content-Length`), malformed payloads (deep nesting, a huge integer, bad UTF-8, non-string attributes, too many events) answered with 400 while the server stays up, and the two-reader limit answering 503 when a slow body holds the slot.

`measure_pages.py` times 32 conclusion-list pages at 1, 4, 8 and 16 requests in flight. Its offline check against a local fake server is not part of the default run (it depends on the machine's load at 16 requests in flight); run it explicitly with `python -m pytest tests/measure_pages.py`. The live timing run is `python tests/measure_pages.py` with `VIEWER_SETTINGS_FILE`, `HONCHO_WORKSPACE` and, if needed, `HONCHO_API_URL` set.

`test_policies.py` covers field-wise block lookup (an empty pair falls through to peer fields), the backend chain, both mode gates (`manual` runs in `scheduler` mode, `document_threshold` does not, and it runs again in `stock`), the enabled gate, instruction files (peer file, backend file, default, database, empty, source tag, flat-name deprecation, oversize warning, missing folder), mtime reload, and the archive regex. The install tests use fake Honcho modules, including a consumer imported before the hook; they check its wrapper identity and the scheduler payload gate. Run-log tests replace the base rerank settings after installation and check refreshed values with and without a per-dream cap.

`test_policies.py` also covers the rerank block: key-by-key lookup and its source, the `RerankSettings` range checks, the `src.honcho_rerank.settings` proxy (base outside a dream, merged inside, base kept and a log line on a value the class refuses), the install with the component, without it (one log line, the hook runs without reranking) and with only the old `src.rerank` fork module (refused, named). An autouse fixture restores `sys.modules` after each test, so the entrypoint tests pass in any order.

`test_rerank_settings.py` covers the `rerank` block in the schema, the example and `validate.py`.

`test_rerank_hook_integration.py` runs the proxy against the rerank component's real `RerankSettings` and client, from `src/rerank/honcho_rerank` in this repository. It skips unless a Honcho v3.5.0 tree is on `PYTHONPATH` (the component imports Honcho). The interpreter is `HONCHO_RERANK_PYTHON`, else the one running pytest; it needs Honcho's dependencies. The test aliases the component as `src.honcho_rerank`, as it is mounted in the container: `HONCHO_RERANK_PYTHON=/path/to/honcho/.venv/bin/python PYTHONPATH=/path/to/honcho python -m pytest tests/test_rerank_hook_integration.py`.

`test_hook_entrypoint.py` covers the deriver entrypoint when `install()` fails: stock mode with every peer on runs stock Honcho, scheduler mode or a disabled peer sets `DREAM_ENABLED=false` and turns off the loaded flag, the status file records the failure, and a hook module that cannot be imported still runs intake. One test runs the policies and entrypoint tests together in a subprocess, in that order.

`test_scheduler.py` covers eligibility (pairs plus each enabled peer with itself), discovery, backup rotation (21 writes leave 20 backups), the `scheduled_by` body, stock mode, the before-replace mtime check and the connection close on a failed query. It does not start `main()`.

`test_backup.py` runs `backup.sh --now` with bash against fake `pg_dump`, `pg_restore`, `psql` and `createdb` placed first on `PATH`: a published dump is listed and checksummed, transient failures are retried up to `BACKUP_ATTEMPTS`, a wrong password or database is tried once, an unreadable or table-less dump is never published. `pg_dump` is also checked to receive `PGPASSWORD` and `PG*` settings but none of the other secrets in the environment. It skips without a bash that has GNU `date` (Git Bash works on Windows). `test_receiver.py` and `test_scheduler.py` check `runtime_env()` (what the process keeps of Honcho's `.env`) and that the re-start happens once.

`test_bridge.py` covers routing, effort mapping for each kind including `max`, the three-level effort precedence (request, stage entry, backend default), the JSON request form per provider kind, the `_KEY` rule for `key_env`, the slot wait counted against the call budget, the 422 for a CLI that is not installed, the socket timeout, the cached-input usage field, log rotation and UTC stamps, a local HTTP stub for `openai-compat` and `anthropic-api`, and a Python stub for the two CLIs. The CLI stub is started through `BRIDGE_EXE` / `BRIDGE_CLAUDE` as a JSON list, which is the Windows-safe form. The call log line is checked with `json.loads`. The shared token is checked on a real socket: every route but a reduced `/health` answers 401 without it, a refused POST is answered without reading its body, and an unset or blank `BRIDGE_TOKEN` leaves the endpoint open.

`test_app.py` covers the dashboard: the page renders, a bad save is refused, a secret-like string is refused and not echoed, a valid save writes the file and keeps a backup, backends can be added and removed (a referenced name is refused), and instruction files resolve, save, fall back and migrate. Workspace instruction writes use a fake API. It does not call Honcho.

`test_app.py` also covers the Rerank page (a save with a `rerank` block, an `api_key` refused and not echoed) and `GET /api/rerank/stats` against a generated telemetry folder (plain and gzipped day files, a non-rerank event, a bad line, an unreadable file, a corrupt gzip body, non-finite and huge numbers with strict JSON output, an oversized line, a scan budget hit, the past-day cache, a bounded duration sample, sent-by-candidates and the last observed counter, the 7-day window).

`test_honcho_config.py` covers the Honcho config schema generator and the config.toml editor: a fixture regenerates to the expected shape, a read merges file values with defaults, a review does not write, a write keeps a comment and an unknown key, a validation error does not write, a compose override stays read-only, the install write moves a primary into its fallback and a `fallback: null` or `overrides: null` removes the table whole, the copy from before Route all is taken once and consumed by either undo (jobs only keeps a later unrelated edit; whole file is byte for byte), both undos refuse a stale mtime or a missing copy, and a write that fails after the file was opened puts the backup back.

`test_models_ui.py` runs the page's routing functions under Node: Route all copies a primary into its fallback and routes it through an already routed job's bridge, keeps a fallback the file has, clears an old effort on a routed job, sets the peer card stage, keeps existing stage entries; a fallback provider change drops `structured_output_mode` and the old overrides; model and effort picks write only `settings.json`; the plain-words column; the embedding row and the Honcho-native branches are gone; a broken `settings.json` blanks only the pages that need it.

`test_global_rerank_reload.py` covers global rerank reload rejection, last-good retention and recovery, with the rerank component's class and the offline JSON schema.

`test_stack_layout.py` covers the folder layout and the services' independence: every log, run record and status file defaults to `/logs` (`LOGS_DIR`), including the telemetry `maintenance.log` and the backup `backup.log`; every settings path defaults to `/config/settings.json`; `deploy/compose.yaml` is the `honcho-tools` project, mounts `LOGS_DIR` into every service that writes logs, `CONFIG_DIR` at `/config` (read-write for the dashboard and the scheduler, read-only for the bridge), `DATA_DIR` at `/data` (dashboard only) and the templates at `/templates`, takes only `config.toml` (into the dashboard) and `.env` from the Honcho folder, does not publish the bridge, has the bridge service with the CLI logins from `SECRETS_DIR`, and has no `depends_on`; the scheduler's backups land in `backups/settings`; `deploy/.env.example` names `HONCHO_ROOT`, `CONFIG_DIR`, `DATA_DIR`, `LOGS_DIR`, `TELEMETRY_DIR`, `BACKUP_DIR` and `SECRETS_DIR` and no `CONTROL_DIR`; the dashboard, the bridge and the scheduler each start with no `settings.json` and none of the other services; the scheduler, dashboard and telemetry images use `python:3.12-slim`, the bridge image uses `node:22-slim` and installs both CLIs without a version, the dashboard and scheduler requirements list direct packages with no version pin, and the bridge image installs the Codex and Claude CLIs only when `INSTALL_CODEX` or `INSTALL_CLAUDE` is `1` (both default to `0`).

`test_app.py` checks that the restart list is the constant `RESTART_ALLOWED` and that no allow file is read, the hook status messages (active, pending, failed with dreams blocked or running stock), DeepSeek off-peak pricing by UTC time, the stage object in the reference check, and the settings API answering a broken file with the reason.

`tests/e2e/test_model_routing_e2e.py` drives the dashboard with Playwright through Route all on the Honcho config page, bridge and effort picks on Models and fallback edits, then runs Honcho 3.5.0's own settings and LLM code, the hook and the bridge against fake providers and fake CLIs, checking the model, effort field and level each provider receives (37 tests). It skips without `HONCHO_TREE` (a Honcho 3.5.0 source tree), an interpreter with Honcho's dependencies (`HONCHO_E2E_PYTHON`), Playwright and Chromium.
